# 보안 감사 보고서

## 요약

현재 구현은 인증이 없는 로컬 개발용 API입니다. 로컬에서 신뢰된 사용자만 접근하는 전제에서는 설계 문서와 일치하지만, 네트워크에 공개하거나 여러 사용자가 공유하는 환경에는 적합하지 않습니다. 가장 큰 위험은 접근 가능한 누구나 모든 할 일을 읽고 변경할 수 있다는 점입니다.

## 감사 범위와 방법

- 기준일: 2026-10-13
- 대상: `app/main.py`, `app/db.py`, `migrations/001_initial.sql`, `pyproject.toml`, API 및 SQLite 설계 문서
- 방법: 정적 코드 검토, 요청 검증과 SQL 생성 경로 확인, 기존 API 테스트 실행
- 범위 밖: 원격 배포 설정, 운영 호스트 방화벽, 외부 침투 테스트, 의존성 취약점 데이터베이스 대조, 저장 장치 및 백업 권한 확인

## 발견 사항

### SEC-01 인증 및 권한 검사가 없음 — 높음

모든 API 경로가 인증 없이 데이터를 조회하고 생성, 수정, 삭제, 복구합니다. 이는 PRD와 TSD의 로컬 개발 전제와 일치하지만, API를 다른 사용자나 네트워크에 노출하면 데이터 기밀성과 무결성을 보호하지 못합니다. Uvicorn 실행 시 기본 루프백 바인딩을 유지하고, 공개 환경으로 옮기기 전 인증, 인가 및 배포 경계 설정을 추가해야 합니다.

### SEC-02 요청 크기와 자유 입력 배열에 상한이 없음 — 중간

제목, 설명, 담당자, 태그, 라벨 문자열 및 배열 요소 수에 애플리케이션 수준 최대 길이, 개수 제한이 없습니다. 큰 JSON 요청은 파싱, DB 저장 및 응답 직렬화 비용을 키울 수 있습니다. 로컬 단일 사용자 환경에서는 위험이 제한적이지만, 공유 환경에서는 메모리, 디스크, CPU 고갈로 이어질 수 있습니다.

### SEC-03 SQLite 파일 권한과 데이터 암호화 및 백업이 보장되지 않음 — 중간

DB에는 할 일 내용과 담당자 이름이 평문으로 저장됩니다. 파일 권한은 실행 사용자와 운영체제의 umask에 의존하며, 암호화, 백업, 보존 정책은 코드와 문서에서 정의되지 않았습니다. 기기 접근 권한이 공유되거나 데이터가 민감한 경우 DB 파일 권한 및 백업 경로를 별도로 보호해야 합니다.

## 확인된 방어

- 요청 본문은 Pydantic 모델로 검증하고 알 수 없는 필드를 거부합니다.
- 조회 필터와 데이터 값은 SQL 바인딩 파라미터를 사용합니다. 동적 SQL 식별자는 코드 내부의 고정 값에서 선택됩니다.
- 제목, 상태, 우선순위는 모델 및 DB 제약으로 검증됩니다. 외래 키는 연결마다 활성화됩니다.
- 목록 페이지 크기는 100으로 제한됩니다.
- 현재 코드 검토에서 사용자 입력을 SQL 문장에 직접 이어 붙이는 경로는 발견하지 못했습니다.

## 권고 순서

1. API를 루프백 밖으로 노출하지 않거나, 공유, 운영 배포 전에 인증, 인가 및 네트워크 경계를 구현합니다.
2. 요청 본문 크기, 문자열 길이, 배열 요소 수에 합리적인 제한을 둡니다.
3. DB 및 백업 파일 권한, 보존 기간, 백업, 복구 절차를 문서화합니다.
4. 배포 전에 잠금 파일 기준 의존성 취약점 검사와 실제 배포 설정 검토를 수행합니다.

## 검증 결과와 한계

기존 `bash scripts/verify.sh` 검증은 감사 시점에 통과했습니다. 이 결과는 기능, 정적 품질 검증이며 보안 인증이나 침투 테스트 결과가 아닙니다. 실제 배포 설정과 운영 파일 권한은 제공된 저장소만으로 확인할 수 없습니다.
