# 성능 감사 보고서

## 요약

테스트 전용 로컬 SQLite DB에서 수정된 동시 초기화 경로를 포함해 총 1,700개 요청을 동시성 상한 100으로 처리했으며 실패는 없었습니다. 다만 이는 단일 프로세스의 인프로세스 ASGI 측정입니다. 운영 서버, 네트워크 처리량을 뜻하지 않습니다. 현재 요청마다 SQLite 연결을 만들고, 연결마다 마이그레이션 확인을 위해 `BEGIN IMMEDIATE` 쓰기 잠금을 획득하므로 불필요한 잠금 경합 가능성이 있습니다.

## 감사 범위와 환경

- 기준일: 2026-10-13
- 앱: FastAPI 동기 엔드포인트, 표준 `sqlite3`, SQLite 파일 DB
- 요청: 신규 DB 첫 조회 100건, 이어서 생성 800건과 목록 조회 800건을 동시 실행
- 동시성: 요청 세마포어 상한 100
- 데이터: 테스트 DB에 생성된 할 일 800건
- 실행: `httpx2` ASGI 전송을 사용한 인프로세스 호출, 임시 DB 파일
- 제외: Uvicorn 소켓, 네트워크, 여러 프로세스, 서버, 원격 디스크, 장시간 안정성, CPU, 메모리 계측

## 발견 사항

### PERF-01 연결마다 쓰기 잠금을 획득함 — 중간

`app/db.py`의 `connect()`는 매 연결마다 `BEGIN IMMEDIATE`로 마이그레이션 검사를 시작합니다. 마이그레이션이 이미 적용된 일반 API 요청도 DB의 쓰기 예약 잠금을 얻고 바로 커밋합니다. SQLite는 쓰기 잠금을 한 번에 하나만 허용하므로 동시 요청이 많을수록 연결 초기화 구간에서 대기할 수 있습니다. 스트레스 테스트의 무오류 결과와 별개로, 중앙값 365ms, p95 1,513ms는 네트워크가 빠진 환경에서도 관측된 값입니다.

개선 방향은 마이그레이션이 이미 적용된 경우 잠금 없이 빠르게 반환하고, 마이그레이션 테이블이 없거나 새 버전이 있을 때만 `BEGIN IMMEDIATE`를 얻은 후 적용 상태를 다시 확인하는 것입니다. 변경 후 같은 cold-start 및 혼합 부하를 반복해 비교해야 합니다.

### PERF-02 목록 직렬화가 연관 테이블을 항목별 조회함 — 중간

`task_dict()`는 각 할 일마다 담당자, 태그, 라벨을 별도 조회합니다. 목록 한 페이지에 최대 100건이 있으면 기본 목록 SQL 외에 연관 정보 조회가 최대 300회 추가될 수 있습니다. 페이지 상한은 비용을 제한하지만 목록 크기와 함께 DB 왕복이 늘어납니다. 페이지 단위로 연관 데이터를 묶어 조회하는 방식으로 줄일 수 있습니다.

### PERF-03 SQLite 쓰기 처리량에는 구조적 한계가 있음 — 참고

SQLite 단일 파일 DB의 쓰기는 직렬화됩니다. 현재는 연결을 요청마다 열고 닫으며 별도 연결 풀이 없습니다. 이는 설계된 로컬 소규모 용도와 맞지만, 여러 프로세스에서 지속적으로 쓰거나 더 높은 쓰기 동시성이 필요하면 WAL 설정과 잠금 대기 측정, 또는 서버형 DB 전환을 별도로 평가해야 합니다.

## 검증

감사 시점 `bash scripts/verify.sh`에서 Ruff, 포맷 확인, strict mypy, 테스트 15개가 통과했습니다. 스트레스 테스트 DB는 임시 디렉터리에 만들어 종료 후 제거했습니다. 테스트는 읽기 전용이며 프로젝트 데이터 파일을 사용하지 않았습니다.

## 우선 권고

1. 이미 최신인 DB 연결에서 매번 쓰기 잠금을 잡지 않도록 마이그레이션 확인 경로를 분리합니다.
2. 연관 데이터 조회를 목록 단위 배치 조회로 바꾸고, 현재 800개 이상 데이터 조건에서 비교 측정합니다.
3. 운영 규모가 정해지면 실제 Uvicorn 프로세스 수, 하드웨어, 데이터 분포를 고정한 재현 가능한 부하 테스트와 p95 목표를 정의합니다.
